# ADR-064: Multiple principal mailboxes are a registry; the account follows the object

Date: 2026-11-12
Status: Accepted

## Context

The principal has more than one Gmail account, for example a personal one and a work one (Google Workspace). Curia managed exactly one, held as two flat settings (`ceo_nylas_grant_id`, `ceo_self_email`) that every ceo-inbox handler, the calendar bootstrap and the outbound gateway read directly. Forwarding one account into the other is not a workaround: it is a poor experience and often blocked by workplace policy.

An EA with delegate access works across both accounts as one job. The hard part is not a second grant. Every action against the principal's mail or calendar now has an account, and the wrong account is a real mistake: personal mail sent from the work address, a work meeting booked on the personal calendar, a draft saved where the principal will not look.

The principal decided that both mailboxes are triaged on an ongoing basis (cadence tunable per mailbox), that calendars are in scope, that choosing the account is an inference from context rather than a rule, and that memory stays shared. Gmail only; the registry must not preclude another provider.

Alternatives considered:

- **A second pair of flat settings** (`ceo_nylas_grant_id_2`). Every handler would need to know how many there are, and nothing would tie a grant to its address, its triage state or its send level.
- **Choosing the account with a rule in code** ("work domain means work"). Real choices are not that regular: the same accountant gets corporate-audit mail at work and tax mail at home.
- **Falling back to the default mailbox when the account is unclear.** The cheapest code, and the exact failure the feature exists to prevent.

## Decision

**A registry.** Mailboxes are rows in `principal_mailboxes` (id, label, address, provider, default flag, triage start, removed-at). The Nylas grant stays a vault secret per mailbox, `principal.mailbox.<id>.nylas_grant_id`; the shared API key is unchanged. The address is read from Nylas when a mailbox is added, never typed by the operator, so a mailbox cannot be wired to the wrong account.

**One service resolves every client.** `PrincipalMailboxes` lists mailboxes and builds the email and calendar client for one of them, on each call, so a grant change needs no restart. An **unknown or removed id is an error, never a fallback to the default.** Callers that pass an existing object id (a draft, a message, an event) get the account from the object: code locates it, and an explicit mailbox that does not hold it is a 404, not a search elsewhere.

**Ids are immutable and never reused.** Removal is a tombstone (the grant is deleted, the row keeps `removed_at`), so everything keyed by an id (send level, cadence, ledger and dedupe records, rules, per-contact preferences) can never attach to a later mailbox, even one labelled "Work" again. The id is a slug (`^[a-z][a-z0-9-]{0,31}$`); `primary` and `default` are reserved.

**Evidence-based choice for new objects.** For a new draft or event, code computes per-mailbox evidence from the recipients (history of sent and received mail, whether the domain matches the mailbox) and the tool refuses to act without a stated `mailbox` once there is more than one. The agent decides from the principal's words, preferences and that evidence; it says which account only when the choice was a real judgement call, and asks when the evidence is split. A correction is cheap (a draft can be moved).

**Upgrade.** A single-mailbox install is migrated at boot from the flat grant into one default row. If neither the grant lookup nor `ceo_self_email` yields an address, the flat grant is served as an in-memory mailbox until the migration succeeds, and the migration is retried on each health-canary tick.

**Health.** Each live mailbox has its own canary (`principal_mailbox:<id>`: grant lookup, one message, calendar list). The default mailbox's result also drives the existing `nylas_calendar` heartbeat, so a deployment's monitor keeps pinging. An outage alerts the principal once per episode, naming the mailbox by label only (never its address or grant), and suggests removing the mailbox if the account is gone.

**Sending follows the draft.** The gateway sends a draft from the mailbox that holds it, at that mailbox's own level (`ceo_inbox/sending` is one level per mailbox id; no key reads `on_request`; amends [ADR-062](062-curia-sends-from-the-principals-mailbox.md)). The autonomous daily cap stays 10 in total across mailboxes, and the thread cooldown also keys on the conversation, so one conversation in two inboxes shares a cooldown. A reply is never sent on its own to, or in answer to, another of the principal's addresses. Holds caused only by a limit (daily cap, cooldown) are reported apart from holds on judgement.

**Triage is a code heartbeat over per-mailbox state.** The hourly cron is replaced by a 15-minute heartbeat in code. It decides which mailboxes are due and starts, or re-wakes, one `inbox-drain` task. It re-wakes only drain tasks it created, with the originator stored on the task, and never upgrades it; a stalled one of its own with no stored originator is closed for a fresh system-originated drain. Drain tasks the old cron flow made are closed once at boot, and the agent never creates one. Triage mode (`triage` on the list tool) is honoured only on a turn of a drain the heartbeat created, and a plain unread listing on such a turn runs in triage mode whatever the model passed, so no other turn can claim a mailbox's batch and no drain can skip the bookkeeping. A drain wake set more than 30 minutes out is pulled in; one the scheduler's circuit breaker suspended is left suspended. The heartbeat runs without the knowledge graph too (its state then lives in memory until a restart), and a `principal_mailbox_triage` health check fails when ticks stop, a mailbox's unread check or triage keeps failing, sent-mail observation fails three runs in a row, or the drain is suspended. The probe uses the same keep rule as triage; because Curia's own mail is recognised only by the From header, a probe that reads five pages of nothing else counts the mailbox as having mail.

- **Cadence and windows.** Each mailbox has its own cadence (default hourly) and weekday-aware window (default 06:00-23:00). A mailbox is due slightly before its interval has elapsed (half a heartbeat, floored), so a drain stamped seconds after a tick does not slip a whole tick. A weekday window that crosses midnight belongs to the day it starts. The drain's start time, not its end, is what the cadence measures, so long drains do not skip ticks. A draining mailbox bypasses its cadence but not its window: a drain pauses at window end and resumes when the window reopens, so overnight triage happens only where the window includes it.
- **Start line, alarm, ceiling.** A mailbox's triage start line keeps old unread mail out of triage; the principal can move it back. A backlog over 100 untriaged messages raises one alarm per episode, and a daily ceiling of 120 batches stops runaway drains; code emails the principal once a day when it does. Listing a mailbox's last batch does not close its drain: the episode closes once the run that triages the batch has finished, so a failed run's retry gets the same messages back.
- **Dedupe.** A message delivered to two mailboxes is triaged once. With two or more live mailboxes every batched message is claimed (one header read each), not only one that names another mailbox: an auto-forwarded or Bcc'd copy names none. The spec's acceptance criterion outranks D4's "only these pay" wording here (R70). A claim held by a mailbox that is no longer live is ignored. The claim key is the normalised Message-ID plus the normalised From address, so a reused or forged Message-ID from another sender does not suppress a real message. If the losing copy cannot be marked read it is kept, not dropped.
- **Reply from the addressed copy.** A reply is drafted in the mailbox the sender wrote to. Code redirects only when exactly one candidate copy matches: same sender, the copy's own Message-ID header equal to the original's, and not in Sent, Spam or Trash. Anything else keeps the triaged mailbox and says why. Mail from any principal address or live mailbox address is never redirected, and is marked Seen only.
- **Rule scope.** An inbox rule may carry a `Mailbox:` line; unscoped rules apply everywhere. An unreadable rules document never blocks removing a mailbox: removal proceeds and reports the rules as not cleaned up.
- **Learning state.** Sent-observe watermarks and the learning keys are per mailbox, so one failing mailbox moves no other. The old global keys move to the migrated mailbox (the one with no start line), not to whichever mailbox is default now; at worst that mailbox re-backfills its sent mail once. Records written before the migration under the fallback id (`mailbox`) belong to that migrated mailbox too (R61), which is why `mailbox` is reserved as a mailbox id.
- **Memory provenance is cheap only.** Checkpoint fact and relationship extraction appends `/mailboxes:<ids>` to its source, from the mailboxes the conversation's ceo-inbox tool calls touched since the last checkpoint (one indexed audit read; a failed lookup keeps the plain source). Memory-store writes carry no mailbox: their source is a rate-limit key built where the mailbox is unknown, and threading it through was ruled out of scope.

## Consequences

- Adding, relabelling, defaulting and removing a mailbox is a console list, not a settings edit, and the setup catalog reports the capability done once one mailbox passes its canary.
- Every handler that used the flat grant must go through the service. A call that cannot name an account fails loudly instead of acting on the wrong one; that is an accepted cost.
- Removal cannot be undone by re-adding the same address: it gets a new id and a clean slate. Stale keyed state is left to age out, except inbox rules: a `Mailbox:` line in `/shared/inbox/rules.md` is edited at removal. A rule scoped only to the removed mailbox is deleted or moved to another live mailbox (the principal chooses; removal is refused without a choice), and a rule scoped to several just drops the id.
- The registry is capped at one live mailbox by a code constant until every handler is converted, so no intermediate release runs a second mailbox through half-converted code.
- While the stack is converting it, calendar keeps the client built at boot, as before the registry: it picks up a new default mailbox or a replaced grant at the next restart. The console says so, and the setup catalog reports a restart as required until then. The acquaintance check (who the principal has written to) reads every live mailbox per call.
- Until the calendar tools are converted, the flat settings remain mirrored from the default mailbox; retiring them waits for that work.
- The principal's memory is not partitioned by mailbox. Confidentiality is about the recipient and the data, not the source account.
- The per-mailbox canary adds three Nylas calls per mailbox per day.
- Triage state written under the fallback id (`mailbox`) while a migration is deferred is not carried over: the migrated mailbox starts fresh, which costs one extra drain, and the old `triage.mailbox.*` keys are left behind.
