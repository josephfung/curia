# ADR-020: Application-layer AES-256-GCM secrets vault in PostgreSQL

Date: 2026-06-07
Status: Accepted

## Context

Every secret the system uses — Nylas API key, Tavily API key, OpenAI key, Google OAuth
credentials — lived as its own environment variable. This creates several problems:

- Secrets can only be rotated with a full redeploy
- OAuth flows that produce tokens dynamically at runtime have no storage mechanism
- A compromised host exposes all credentials as plaintext in the process environment
- The audit trail (`secret.accessed`) cannot show where a value came from

**Alternatives considered:**

- **External KMS / HashiCorp Vault:** Stronger separation of concerns but significant
  operational overhead for a single-operator deployment. Deferred — the `SecretsService`
  interface is designed to be swappable if a KMS becomes warranted later.
- **Envelope encryption (per-key DEKs):** Useful when different keys need different
  access controls, but overkill for a deployment with a single trusted operator.
  Single-key AES-256-GCM is sufficient and simpler.
- **Separate `oauth_tokens` table with an `oauth` type column:** Bakes consumer semantics
  into the storage layer. Every new structured secret kind (browser sessions, service-account
  blobs) would require a migration. Rejected in favor of structural typing.
- **Async `ctx.secret()` API:** Changing `secret(name): string` to
  `secret(name): Promise<string>` would require updating ~15 skill handlers and breaks
  the synchronous skill-context contract. Rejected in favor of a per-invocation pre-warm
  cache that async-loads declared secrets before `ctx` is constructed.

## Decision

Store secrets encrypted at the application layer (AES-256-GCM, 128-bit auth tag,
12-byte random IV per write) in a PostgreSQL `secrets` table. The single
`SECRET_ENCRYPTION_KEY` environment variable (32 bytes, base64) unlocks all stored
credentials; a DB dump without the key reveals nothing.

**Structural typing, not semantic typing.** The `value_format` column distinguishes
`'string'` (raw text) from `'json'` (JSON-serialized object). It does not encode
purpose — OAuth token sets, browser sessions, and any future structured secret are
all `'json'` values whose shape is a convention owned by their consumer. This means
new secret kinds require no schema migrations.

**Synchronous `ctx.secret()` preserved** via a per-invocation pre-warm cache.
`ExecutionLayer.invoke()` async-loads all manifest-declared secrets into an in-memory
map before constructing `ctx`, so the skill-facing API remains synchronous. Vault hits
take precedence; env-var fallback is preserved for incremental migration.

**Fail closed at startup.** A missing or malformed `SECRET_ENCRYPTION_KEY` is a
hard startup failure with a clear error message. The key is auto-generated by the
setup script (`openssl rand -base64 32`), matching the pattern used for `API_TOKEN`.

## Consequences

**Easier:**
- Secrets can be created, rotated, and revoked at runtime without redeployment
- OAuth token sets (and any other structured credentials) have a first-class storage path
- A compromised DB dump without the key reveals nothing
- The `secret.accessed` audit event gains a `source` tag (`vault` | `env`) showing
  migration progress as secrets move from `.env` to the vault
- Key rotation is a single transactional re-encrypt (`scripts/rotate-secret-key.ts`),
  not a credential-by-credential redeploy

**Accepted trade-offs:**
- `SECRET_ENCRYPTION_KEY` itself must remain an environment variable (cannot live in
  the vault it unlocks) — documented in the follow-up migration issue (#911)
- The env-var fallback path must be maintained until all secrets are migrated (#911)
- Single-key design means a compromised `SECRET_ENCRYPTION_KEY` exposes all secrets —
  acceptable for single-operator deployments; envelope encryption remains an option
  if multi-tenant or multi-operator scenarios emerge
